# FlexPlan

**Планировщик, в котором у задач есть длительность.** Задачи раскладываются по часам на календаре
(день / неделя / месяц / год), поэтому сразу видно, что реально влезает в день, а что — самообман.
Задачи без даты лежат в буфере и перетаскиваются на сетку.

Роль: единственный разработчик — продукт, архитектура, фронтенд, бэкенд, инфраструктура, биллинг,
лендинг, промо. Период активной разработки: июнь — июль 2026, продукт в проде с подпиской.

---

## Продуктовый объём

Десять функциональных «столпов» в одном приложении: календарь с четырьмя масштабами · буфер задач ·
канбан-доски · заметки (Markdown, вики-ссылки, граф связей, импорт vault-архива) · трекер привычек ·
фокус-таймер · AI-ассистент · командные пространства · статистика · Pro-подписка.

Платформы: веб и PWA, нативная обёртка для macOS на Tauri 2, мобильное приложение на Expo/React Native,
iOS-сборка через Capacitor. Интерфейс на русском и английском, светлая и тёмная темы.

## Стек

**Фронтенд:** React 19 + TypeScript + Vite 7. Своя реализация pointer-drag вместо готовой
drag-and-drop библиотеки (нужен был контроль над попаданием в часовую сетку). `date-fns`, `i18next`,
`react-markdown` + GFM, `zod` для валидации границ данных, Sentry опционально и динамическим импортом.
Роутера нет — навигация реализована как машина состояний, что для приложения-одного-экрана оказалось
проще и быстрее react-router.

**Бэкенд:** Node.js + Express + TypeScript, PostgreSQL 16 через драйвер `pg` — сырой параметризованный
SQL без ORM, транзакции руками. Аутентификация на `jsonwebtoken` + `bcryptjs`, свой WebSocket-слой на
`ws`, Web Push через VAPID, почта через SMTP, rate-limit на публичных ручках.

**Инфраструктура:** VPS, Docker Compose (база + API), хостовый nginx отдаёт SPA и проксирует API.
Скрипты деплоя, бэкапов и watchdog-а — часть репозитория.

## Архитектурные решения, которыми я доволен

### Offline-first синхронизация с конфликт-резолюцией

Приложение изначально работает локально: без сети и даже без аккаунта. Онлайн — это надстройка, а не
предпосылка. Из этого выросла отдельная подсистема синхронизации:

- локальное состояние в `localStorage` + очередь мутаций в IndexedDB;
- пер-сущностные мутации вместо «залить весь стейт целиком»;
- разрешение конфликтов — row-level last-write-wins по `updated_at`;
- удаления через tombstones, иначе сущность, удалённая на телефоне, возвращалась с ноутбука при
  следующей синхронизации;
- баннер статуса синхронизации в UI, чтобы состояние «есть несохранённое» было видимым, а не магическим.

Это самая нетривиальная часть продукта: почти все баги с «пропавшими задачами» жили именно здесь, и
именно поэтому протокол синхронизации закрыт автотестами.

### Realtime без лишней инфраструктуры

Вместо Redis pub/sub или PostgreSQL LISTEN/NOTIFY — один WebSocket-сервер на процесс и in-process
шина событий. Сервер шлёт клиенту минимальное сообщение вида «в этом пространстве изменилась вот эта
таблица», а клиент сам до-пуливает только затронутый скоуп. Плюсы: нет ещё одного сервиса в
проде, нет рассинхрона схемы событий и данных, трафик минимальный. Минус — не масштабируется на
несколько инстансов; это осознанный компромисс под текущую нагрузку, и место для расширения известно.

### Аутентификация и подписка

Короткоживущий access-JWT в памяти клиента и refresh-токен в httpOnly-cookie на 30 дней; прозрачное
обновление на первом 401, отдельная ветка выдачи токена для десктопа, где cookie недоступны. Pro-гейт
реализован как middleware перед роутами, а не проверками в каждом хендлере, — включается и
выключается конфигурацией, что важно для локальной разработки и тестов.

### Одно доменное ядро на веб и мобайл

Доменная логика, клиент API, синхронизация и словари i18n вынесены в отдельный пакет монорепозитория
и потребляются **как TypeScript-исходники** сразу двумя сборщиками — Vite для веба и Metro для
мобильного приложения. Без промежуточной сборки пакета: правка логики синхронизации мгновенно
применяется на обеих платформах, и невозможно получить ситуацию «на вебе починили, на мобайле забыли».

### Живучесть фронтенда после деплоя

Две защиты, которые появились из реальных инцидентов:

- **boot-watchdog** в HTML: если через 30 секунд корневой узел пуст, пользователь видит понятную
  ошибку загрузки вместо белого экрана;
- **self-heal service worker**: после деплоя старый SW может отдать несуществующий чанк и уронить
  lazy-import — приложение перехватывает эту ошибку, снимает регистрацию SW, чистит Cache Storage и
  делает один контролируемый reload под guard-ом от циклов.

## Интеграции

Платёжный провайдер (подписка, автопродление по расписанию, вебхуки) · Google Calendar (двусторонняя
синхронизация событий) · Web Push с VAPID и напоминаниями по шедулеру · SMTP для писем ·
внешний LLM через OpenAI-совместимый SDK для AI-ассистента · аналитика и мониторинг ошибок.

## Проверка качества

Vitest + Testing Library на доменную логику и критичные UI-инварианты, Playwright для сценарных
проверок, ESLint с type-aware правилами, `tsc -b` в сборке. Отдельный архитектурный документ,
перепроверяемый чтением реального кода, — чтобы документация не расходилась с продуктом.

## Что бы сделал иначе

- Ввёл бы протокол синхронизации сразу версионированным (сейчас это далось миграцией «sync-v2»).
- Не откладывал бы вынос доменного ядра в пакет до появления мобильного приложения — часть логики
  успела продублироваться и её пришлось сводить.
- Часть UI-состояния стоило держать в URL с самого начала: машина состояний вместо роутера ускорила
  старт, но deep-link и восстановление вкладки пришлось добавлять поверх.
